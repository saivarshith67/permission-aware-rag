**ABSTRACT** Retrieval-Augmented Generation (RAG) enhances large language models (LLMs) by integrating external knowledge sources, which significantly improves response accuracy and contextual relevance. However, most existing RAG research implicitly assumes that all retrieved content is equally accessible to any user. This approach fails to address the complex, fine-grained access control required in enterprise environments in which data originates from multiple, independently governed sources. Attempting to merge heterogeneous authorization models, such as RBAC and ABAC, often leads to significant compliance burdens and unintended data exposure. To address this issue, we propose a permission-aware RAG framework that enforces resource-level access control by directly interfacing with provider-controlled Identity and Access Management (IAM) systems. By performing real-time permission validation against native IAM endpoints without requiring policy merging, this design preserves governance boundaries and ensures compliance. We implemented a prototype and conducted a comprehensive evaluation using a multi-hop QA benchmark. The evaluation included scenario-based qualitative analysis to verify policy enforcement, large-scale quantitative validation that confirms its scalable policy enforcement and quantifies the impact of access levels on answer quality. Results demonstrate that our framework provides secure, scalable information retrieval while maintaining strict adherence to diverse access policies across multi-resource environments.

**II. RELATED WORK**

*A. ACCESS CONTROL NEEDS IN RAG SYSTEMS* RAG systems are increasingly used in multi-resource environments where knowledge is distributed across diverse data sources. For example, in many enterprises, data resources are distributed across multiple departments, services, and infrastructure environments. In healthcare organizations, patient records may be stored separately within hospitals, clinics, and research labs due to privacy policies, organizational boundaries, and system silos. In finance, investment reports, client data, and regulatory documents are often managed using different cloud providers, on-premise servers, or SaaS platforms depending on departmental budgets, policies, and compliance requirements. Such fragmented environments make centralized data integration challenging and result in complex multi-resource settings that RAG systems must operate within [12]. Each data source is governed by its own access control policies and regulatory requirements. Healthcare data must comply with HIPAA [13], GDPR [14], and local privacy laws. Financial data is subject to strict industry- specific regulations, and government documents often require strict security clearances. Furthermore, these policies are implemented using heterogeneous models such as RBAC or ABAC, making unified enforcement complex. Without aligning retrieval processes with these diverse policies, RAG systems risk unauthorized disclosure, policy conflicts, and regulatory violations [15], [16]. Therefore, RAG systems require fine-grained (resource-specific), user-specific, and real-time access validation mechanisms. However, existing RAG frameworks lack built-in capabilities to perform such dynamic authorization at query time. The need for such mechanisms has been formally recognized in recent security analyses of RAG systems. For instance, a systematic review by Ammann et al. identifies *Retrieval Data Leakage* as a primary threat and proposes *Access Limitation* as a critical mitigation strategy [17]. This underscores the academic and practical importance of developing robust access control frameworks specifically for RAG. Therefore, a central challenge in RAG security research

*B. REPRESENTATIVE APPROACHES TO INTEGRATED* *ACCESS CONTROL* Prior research has proposed multiple strategies for integrating access control into RAG systems. As illustrated in Fig. 2, these approaches can be broadly categorized into centralized and distributed architectures, depending on how documents are stored and policies enforced. **Centralized frameworks** consolidate documents from various sources into a single vector database and apply internal filtering mechanisms. For example, Chen et al. [18] proposed a proof-of-concept implementation that maintains a centralized vector database alongside an internal permission store. A more structured centralized approach is seen in VAULT, which models access control rules directly within a Knowledge Graph [19]. However, this model necessitates a complex and continuous synchronization of its internal node-level access attributes with the original IAM systems, creating a significant challenge for maintaining real-time policy consistency, especially in heterogeneous environments. While these different architectures enable streamlined management within a single policy domain, they share a critical limitation: they require merging diverse access control models, such as RBAC [10] and ABAC [11], into a unified enforcement layer. This process is not only operationally burdensome but also introduces semantic mismatches and risks of unintended data leakage or privilege escalation due to flawed policy mapping. **Distributed frameworks**, by contrast, maintain policy autonomy by enforcing access control within each data provider’s environment. For instance, MediRAG [20] implements a federated retrieval system across hospitals, using policy-based access control (PBAC) [11] at each node to ensure that organizations can independently define and enforce policies. This architecture preserves data sovereignty and aligns well with compliance requirements in sensitive domains like healthcare. However, MediRAG assumes that all nodes adopt a uniform PBAC model, which is often unrealistic. Real-world enterprises frequently employ
heterogeneous IAM systems such as GCP IAM, AWS IAM, or Keycloak, each with its own authentication workflows, policy languages, and role hierarchies. Requiring standard- ization across such diverse systems introduces substantial adoption barriers. Furthermore, MediRAG lacks integration with these native IAM systems, making centralized governance and cross-domain identity management difficult to scale. We address this gap by delegating authorization to each provider’s native IAM at retrieval time, rather than consolidating policy management. In environments where heterogeneous access control models such as RBAC, ABAC, and custom policies coexist across administrative domains, requiring centralized policy consolidation becomes highly impractical. Centralized RAG architectures struggle with the complexity and risk of merging diverse policies, while distributed frameworks often rely on a unified access control model that does not reflect real-world diversity. These limitations underscore the need for an alternative approach that can respect policy autonomy while still enabling efficient retrieval. To this end, we propose Permission-Aware RAG, a framework that supports fine-grained access control through real-time permission validation by directly interfacing with native IAM systems. This design enables secure and scalable retrieval across heterogeneous multi-resource environments without requiring structural reconfiguration.

*C. FEDERATED IDENTITY AND ZERO TRUST* *ARCHITECTURES* While *Federated Identity Management (Federated IAM)* provides the foundational layer for authentication in multi-service environments, recent surveys highlight persistent challenges such as privacy risks, attribute aggregation, and revocation [21], [22]. Privacy-preserving extensions like *PRIMA* enable selective disclosure and unlinkability between identity providers (IdPs) and service providers (SPs) [23]. Reference models such as the *Reference Service Model* *Framework for Identity Management* attempt to standardize identity management architectures across centralized, federated, and user-centric models [24]. However, none of these approaches address the subsequent, more granular challenge of real-time, per-document authorization within retrieval-augmented systems. Our Permission-Aware RAG framework is designed to solve precisely this challenge. It operates on the principles of a *Zero Trust Architecture (ZTA)* [9], which mandates continuous verification for every access request. While Federated IAM establishes *who* the user is, our framework determines *what* that authenticated user is allowed to see at the moment of retrieval. By delegating this check to native IAM systems, we enforce ZTA’s *least privilege* principle for every retrieved resource, bridging a critical gap between federated authentication and practical, secure, access-controlled retrieval in modern enterprise environments. This approach is also compatible with existing enterprise Single Sign-On

(SSO) mechanisms, as it leverages the same IAM endpoints used for federated authentication.

**III. METHODOLOGY**

*A. MOTIVATION FOR IAM-BASED INTEGRATION* Modern enterprises use IAM systems such as AWS IAM, GCP IAM, Azure Active Directory (Azure AD), and Keycloak to manage fine-grained access control across their resources. These systems provide authentication, authorization, RBAC/ABAC policy support, audit logging, and version-controlled policy management to ensure security and regulatory compliance. For example, depending on service requirements, resources may be deployed across GCP, AWS, or on-premise environments. Organizational policies may mandate that certain data be processed exclusively on-premise for compliance reasons, while other services leverage cloud-based solutions. Although consolidating diverse access control policies into a single, unified policy across all services and organizations may be considered ideal, achieving such integration in practice requires extensive legal reviews, cross-institutional policy reconciliations, and thorough conflict analysis across heterogeneous access models[25]. These processes, such as policy mapping and role harmonization, are time-consuming and operationally burdensome, often delaying the deployment of Retrieval-Augmented Generation (RAG) systems that require timely integration with external knowledge sources. To address this challenge, our framework integrates RAG systems with existing IAM infrastructures, enabling real-time access validation without requiring full policy unification. This design maintains the independent policy governance of each organization while ensuring compliance, operational feasibility, and immediate deployability. By leveraging the trusted IAM endpoints operated by each provider, the system maintains consistency with institutional policy structures (e.g., RBAC, ABAC, resource policies) and prevents semantic mismatches. It also integrates seamlessly with native IAM functionalities such as audit logging, policy evaluation, and token validation, thereby minimizing legal and compliance risks in multi-resource environments.
*B. THREAT MODEL* Our framework’s security model is grounded in the *Zero* *Trust Architecture (ZTA)* principle of *never trust, always* *verify*, treating every document access request as a distinct transaction that requires explicit authorization [9]. Based on this, we use the *STRIDE* model to define our scope [26].
- **Information Disclosure (In Scope):** This is the primary threat our framework prevents. Conventional RAG systems implicitly trust any retrieved document, creating a significant risk of leaking sensitive information. Our framework mitigates this by enforcing real-time, per-document authorization against native IAMs.
- **Elevation of Privilege (In Scope):** We address unin- tentional privilege escalation at the data access layer. By delegating authorization checks to the authoritative source (the native IAM), our framework prevents flawed logic, such as faulty policy merging, from granting users access to data beyond their intended scope.
- **Spoofing, Tampering, Repudiation, and Denial of** **Service (Out of Scope):** Our framework focuses specifically on authorization and assumes other foundational security layers are in place. We assume user identity verification (spoofing) is handled by upstream authentication systems (e.g., SSO). Threats to data integrity (tampering), auditability (repudiation), and service availability (denial of service) are considered out of scope, to be addressed by underlying infrastructure security.
*C. SYSTEM ARCHITECTURE* The Permission-Aware RAG framework is designed to enable access control across multi-resource environments without requiring central policy merging. As illustrated in Fig. 3, the architecture’s modular pipeline is centered around the Permission Retriever, which utilizes a Credential Manager and an IAM Adapter to filter documents retrieved from the Vector Store, using details from the Metadata Store. This design ensures both maintainability and scalability. Each module addresses specific operational needs. For example, by separating the Credential Manager from the IAM Adapter, security credentials can be managed and updated independently of permission validation logic, ensuring flexi- bility and security. To enforce user-specific access rights, document permissions are delegated to the IAM systems operated by each service provider. This design preserves the independent policy governance of each organization while enabling real-time authorization checks without requiring unified policy consolidation. By avoiding the need to merge policies, the framework mitigates risks of semantic conflicts and ensures compatibility with heterogeneous access control models deployed by different institutions. The system operates in two primary stages: the Indexing Stage and the Query Stage, described below.
1) INDEXING STAGE
- (a) Data are collected from each service or organization and sent to the Data Ingestion Manager.
- (b) The Data Ingestion Manager assigns a globally unique resourceID to each resource, serving as a persistent identifier linking document chunks to their provider and IAM information, while also enabling efficient metadata updates and deletions when resource information changes over time.
- (c) Document chunks, their corresponding embeddings, and the associated resourceID are stored in the vector store as vector_meta, referring to embedding

This indexing stage normalizes and stores all metadata and embedding information required for retrieval and access control. Its successful execution determines real-time search speed and validation efficiency in the subsequent query stage, enabling fast and accurate Permission-Aware RAG responses even in large-scale environments containing millions of documents.

2) QUERY STAGE
- (1) The user submits a query, which is encoded via an embedding model.
- (2) The vector store is searched to identify semantically relevant documents.

- (6) The IAM Adapter receives permission requests for relevant documents and concurrently verifies them with IAM services. It then returns the validation results, enabling the system to filter out unauthorized documents.
- (7) Filtered authorized documents and the user query are passed to the LLM to generate the final answer. The architecture is designed to support horizontal scaling
of the Permission Retriever and IAM Adapter modules, which is expected to handle high query volumes with minimal

By delegating access validation to native IAM systems rather than consolidating policy management, the framework mitigates risks such as permission misconfiguration (incorrect access settings granting unintended permissions), policy drift (gradual divergence between intended and actual policies over time), and privilege escalation (users gaining higher privileges than originally authorized). This decentralized validation model ensures that each data provider retains full control over resource access decisions, aligning with security and compliance requirements.

*D. CORE MODULES*
1) DATA INGESTION To provide a scalable and reliable entry point for all external resources, the Data Ingestion module is responsible for collecting and ingesting resources from diverse data sources into the Permission-Aware RAG framework. Each ingested resource is assigned a globally unique identifier called resourceID, generated as a UUID, ensuring persistent and collision-free identification across the system. Simultane- ously, the module stores the original data source identifier as local_resource_id, which references the resource’s native identifier within its originating platform or repository. This dual-identifier design significantly enhances traceability by maintaining both a system-wide unique reference (resourceID) and the source-specific identifier (local_resource_id). Such structure enables reliable CRUD operations, ensuring that modifications or deletions can be efficiently propagated back to the original data source while preserving consistent mappings within the RAG system.

The detailed metadata schema for each resource, including provider-specific parameters required for permission validation, is provided in AppendixA. A key design principle is the decoupling of static vector embeddings from dynamic metadata. The vector store holds embeddings linked by resourceID for rapid retrieval, while the metadata store contains information prone to operational changes, such as file names and storage locations. This separation is crucial for maintainability and efficiency, as it allows metadata to be updated independently without the costly re-indexing of vector embeddings. In summary, the Data Ingestion module combines a dual-identifier mechanism for robust traceability with a decoupled storage architecture for operational efficiency. This approach provides a scalable and maintainable foundation, ensuring that permission-aware retrieval can function effectively in complex, dynamic enterprise environments.

2) CREDENTIAL MANAGER The Credential Manager module serves as an orchestration gateway for obtaining, managing, and providing service-specific credentials required for authorization checks across heterogeneous platforms such as GCP, AWS, and Keycloak. Its primary purpose in production environments is to integrate with external Identity Providers (IdPs) such as Active Directory, Okta, or enterprise Single Sign-On (SSO) solutions, leveraging authentication and authorization protocols including Security Assertion Markup Language (SAML)[27], OAuth2[28], and OpenID Connect (OIDC)[29]. Through these integrations, it dynamically retrieves and refreshes tokens to enable seamless, compliant, and auditable access to resources. In this experimental implementation, however, the Credential Manager replaces dynamic token retrieval with direct storage and lookup of static credentials, such as pre-generated service account keys or access keys, to simplify deployment and facilitate reproducible evaluation of permission-aware retrieval workflows. For example, GCP uses pre-generated service account keys, AWS uses access key ID and secret access key pairs, and Keycloak-based local services store client credentials in a static form. While this approach does not reflect production-scale orchestration, it simplifies the credential retrieval logic for evaluating the core permission validation functionality of the framework. To optimize performance and reduce redundant authorization requests, the framework employs an internal caching mechanism for credentials with a time-to-live (TTL) configuration. This TTL-based caching ensures that credentials are reused within their validity window, while expired tokens are automatically refreshed to enforce security policies such as key rotation requirements [30]. In summary, while the experimental Credential Manager uses static credentials for simplicity, its modular design anticipates integration with dynamic, secure, and compliant credential orchestration mechanisms in production environments. To further clarify this production-grade integration,
we detail the complete dynamic credential orchestration workflow, which integrates with enterprise SSO systems, in Appendix B.

3) IAM ADAPTER The IAM Adapter module is responsible for validating user access permissions for each retrieved document. It leverages platform-specific SDKs to communicate with the native IAM service of the document’s provider (e.g., GCP, AWS, or Keycloak). To prevent access validation from becoming a performance bottleneck, the adapter employs a multithreading-based architecture to execute these I/O-bound permission checks in parallel. The adapter’s modular design and specific implementation details are further described in Appendix C. Overall, the IAM Adapter provides a robust and extensible solution for validating user access permissions across heterogeneous services. **IV. EXPERIMENTAL SETUP**
*A. EXPERIMENTAL OVERVIEW* The primary objective of this experimental evaluation is to assess whether the proposed Permission-Aware RAG framework can accurately and effectively enforce document-level access control in realistic, heterogeneous multi-resource environments without requiring centralized policy merging. To achieve this, three distinct experiments were designed: (1) a scenario-based qualitative evaluation to analyze the correct application of access control rules in realistic user-policy-resource combinations across GCP, AWS, and Keycloak; (2) a large-scale quantitative evaluation to measure permission filtering scalability and its resulting impact on answer quality; and (3) a latency evaluation to measure the performance overhead of real-time permission validation by varying retrieval volume and concurrency. All experiments were conducted on a server equipped with an Intel Xeon Gold 6230 CPU, 754GB of RAM, and three NVIDIA Tesla V100 GPUs. The experiments were conducted using the HotpotQA dataset, selected for its multi-hop questions that require retrieving information from multiple documents, simulating complex enterprise environments. Document contexts were encoded using the all-MiniLM-L6-v2 Sentence Transformer model into 384-dimensional embeddings and stored in a centralized FAISS-based vector store. For final answer generation, the gpt-4o-mini model served as the LLM backend. To simulate a multi-cloud environment and ensure consistent network conditions, cloud resources were hosted in GCP’s asia-northeast3 and AWS’s ap-northeast-2 regions.

**VI. CONCLUSION AND FUTURE WORK** This paper introduced the Permission-Aware RAG framework, a novel architecture for enforcing real-time, document-level access control in retrieval-augmented generation systems operating across heterogeneous, multi-resource environments. By delegating access validation to native IAM systems, the framework preserves policy autonomy and eliminates the need for centralized policy merging, which is often error-prone and operationally burdensome. The experimental evaluations collectively demonstrate that the framework reliably enforces fine-grained permissions, scales effectively across diverse services, and maintains stable and predictable low-latency performance suitable for real-time applications. These findings confirm the framework’s ability to support secure, policy-compliant retrieval without compromising responsiveness or answer quality. Its plug-and-play design allows seamless integration with existing IAM infrastructures such as RBAC and ABAC, enabling flexible RAG deployment across independently governed services. In contextualizing the advantages of our design, we com- pare it against alternative approaches. First, *manual policy* *merging*, as demonstrated by our qualitative evaluation baseline (the CG user), is error-prone and can introduce critical security risks like data leakage. This approach is not only operationally burdensome but often leads to a loss of policy granularity during translation. Second, *static filtering*, which involves pre-building separate indexes for each user role or group, is fast but highly inflexible. It requires index regeneration upon permission changes, causes unnecessary data duplication when the same document is shared across multiple groups, and inevitably suffers from stale permission issues in dynamic environments. In contrast, *index-level* *controls* filter based on metadata within a single index, which can emulate RBAC and simple ABAC. However, this approach requires continuous metadata synchronization for complex or dynamic policies and struggles to reflect time-based conditions or hierarchical resource policies in real-time. Moreover, query costs can increase with the number of filter conditions, leading to performance degradation

in large-scale environments. Our framework’s approach of *delegating validation to native IAMs in real-time* directly overcomes these limitations. It eliminates the risks of manual policy mapping, ensures that the most current permissions are always enforced, and leverages the full expressiveness of IAM, thereby providing superior security, dynamism, and compliance in complex enterprise environments. Despite these strengths, several practical challenges and limitations remain. The framework’s reliability is influenced by the availability and responsiveness of external IAM services, making it vulnerable to issues like IAM outages. Furthermore, while the dataset utilized in this study was well-suited for evaluating the core mechanisms of multi-hop question answering and permission-aware retrieval, it does not fully capture the scale, heterogeneity, and policy complexity of proprietary enterprise environments. Consequently, the results should be interpreted with this limitation in mind, and future work should extend the evaluation to more diverse datasets and realistic IAM configurations. To address these limitations, future work will focus on enhancing the framework’s robustness for production environments. We have identified several edge cases, such as those mentioned above, and a detailed breakdown of these cases with candidate mitigation strategies is outlined in AppendixFas preliminary considerations. Key areas of future research will include implementing robust TTL-based caching to handle API rate limits and reduce latency, and introducing health checks with fallback mechanisms to improve fault tolerance. Additionally, we plan to explore new retrieval strategies to enhance answer quality in low permission coverage scenarios. Finally, to further enhance security, we aim to encrypt both document embeddings and metadata within the vector store. In summary, the Permission-Aware RAG framework establishes a secure, scalable, and adaptable foundation for building trustworthy, access-controlled AI systems in real-world, multi-tenant environments. The implementation of the proposed framework is publicly available as open-source code on GitHub[35].

**APPENDIX B PRODUCTION-GRADE CREDENTIAL** **ORCHESTRATION WORKFLOW** This appendix details the practical workflow for the Credential Manager in a production environment. It illustrates how the framework implements **Identity Federation** by integrating enterprise Single Sign-On (SSO) systems with cloud Security Token Services (STS). The process, illustrated in Fig.7, adheres to the principle of least privilege by avoiding the use of static, long-lived keys. The workflow consists of the following key stages:

- **User Authentication via SSO (Steps 1-5)** When a user first accesses the RAG application, the
RAG framework redirects them to a corporate Identity Provider (IdP) like Okta or Azure AD for authentication. Upon successful authentication, the IdP issues a primary identity token (e.g., an OIDC ID Token or a SAML Assertion), which is returned to the RAG framework. The framework validates this token to establish a secure, authenticated session for the user. This initial step handles user authentication securely without the RAG system ever handling user passwords.

- **Dynamic & Temporary Credential Issuance (Steps 6-**
**8)** Once authenticated, the user submits a query to the RAG framework (Step 6). The **Credential Manager** then uses the user’s identity information from the established session to request a temporary, short-lived credential from the cloud provider’s Security Token Service (STS) (Step 7). The STS, in turn, issues the temporary credential back to the framework (Step 8). This ‘‘token exchange’’ process is central to the framework’s security, as it ensures that permissions are granted dynamically and expire automatically.
- **Permission-Aware Resource Access (Steps 9-11)** The **IAM Adapter** uses the newly issued temporary credential to make an authorized API call to the native cloud service. The cloud provider’s IAM service validates the credential and the requested permission, returning a success or failure response (Step 10). Based on these real-time checks, the RAG framework processes only the authorized documents to generate and return the final, filtered response to the user (Step 11). This end-to-end workflow demonstrates how the
Permission-Aware RAG framework can be securely deployed in complex enterprise environments by integrating with existing identity management systems and enforcing dynamic, just-in-time access control.

**APPENDIX C IAM ADAPTER IMPLEMENTATION DETAILS** The IAM Adapter is designed with a modular and extensible architecture to validate user access permissions across heterogeneous platforms. Each implementation class extends a shared interface defined in the abstract base class AccessControlBase, which declares the common check_permission() method. Service-specific classes, including GCPAccessControl, AWSAccessControl, and KeycloakAccessControl, inherit from this base class and implement the method using their respective native IAM APIs and SDKs. Specifically, the boto3 library is used for AWS, the google-cloud-storage SDK for GCP, and REST API endpoints for Keycloak-based services. To enhance system scalability and response performance, the IAM Adapter employs a multithreading-based architecture. Permission checks are predominantly I/O-bound due to network API calls, and executing them in parallel prevents access validation from becoming a bottleneck in the retrieval pipeline. The current implementation leverages Python’s

ThreadPoolExecutor class from the concurrent library to manage thread pools and schedule tasks concurrently, ensuring efficient resource utilization. Furthermore, the adapter’s modular design is intentionally extensible to support more advanced parallel processing schemes. For instance, in large-scale production environments, the adapter can be readily integrated with multipro- cessing architectures that leverage distributed task queues such as Celery or RabbitMQ. These systems enable the distribution of permission-checking tasks across multiple worker nodes, thereby further increasing throughput and reliability. Overall, the IAM Adapter provides a robust and extensible solution for validating user access permissions across heterogeneous services. By leveraging platform-specific SDKs, parallel execution, and support for advanced distributed processing, it ensures both secure and efficient operation within the Permission-Aware RAG framework.
